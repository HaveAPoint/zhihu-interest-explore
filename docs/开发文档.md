## 1. 建议技术切分

三块独立发，用同一份后端。

插件：Chrome Extension Manifest V3。内容脚本只匹配 `https://zhuanlan.zhihu.com/p/*`。内容脚本负责选区、蒙版 DOM、高亮、箭头、局部树渲染、挤压布局。扩展页或独立网页负责 OAuth 回调后的登录态。不要用 Side Panel 放树。

独立页：普通 Web 应用，单独域名或 `app.` 子域。横向树用画布（SVG 或 Canvas + HTML overlay 均可），必须能平移缩放。节点详情是普通 DOM。

后端：负责 OAuth、CRUD、调模型和搜索。插件不直接持有模型密钥。

黑客松可以前后端同一仓库。建议目录：

```
plugin/          浏览器插件
web/             独立页
server/          后端
disciplines/     三棵学科树的 JSON skill
docs/            本目录，只读
```

语言不强制。独立页和插件 UI 若用同一套组件，局部树节点的短标题、淡黄色、金 tag 必须两边视觉一致。

## 2. 数据模型

所有 id 用 uuid。时间用 ISO-8601 UTC。

### User

id, zhihu_user_id, zhihu_name, created_at

### Discipline

id, major（大类，如「人工智能」）, name（具体学科，如「Agent 应用开发」）, skill_path, created_at, origin（`preset` | `generated`）

黑客松三行预置：

| major | name |
| 人工智能 | Agent 应用开发 |
| 心理学 | 认知心理学 |
| 计算机系统 | 分布式系统 |

### GlobalNode

id, discipline_id, parent_id（根为 null）, title, aliases[]（字符串数组，用于匹配「SGD」和「随机梯度下降」）, definition（一句）, path（从根到此的 title 数组，冗余方便展示）, is_personal（个人补充）, sort_order

点亮不存字段。查询时：该节点是否存在至少一条 ExplorationRecord。全亮 tag 也不存：查询时该节点已点亮且所有直接子节点都已点亮（空子节点即叶子：自身点亮则带全亮 tag）。

熟练度：整数 0–5 或 null，存在 GlobalNode 上，仅用户手改。默认 null，界面显示为未设置。不要用它排序。

### Article

id, zhihu_id, url, title, tags[], lead（首段文本）, discipline_id（判定一次后写入，可被用户改标签时更新）, created_at

可选 snapshot_html 或 snapshot_text：开第一棵树时静默写入。产品不承诺用它恢复，但存了不亏。

### LocalTree

id, user_id, article_id, discipline_id, global_node_id（可 null，表示待挂靠）, match_candidates（JSON，见下）, anchor_paragraph（引文整段）, anchor_highlight（段内实际选中）, anchor_mark_count 用节点数实时算, created_at, updated_at

match_candidates 结构：

```
[
  { "global_node_id": "...", "title": "...", "degree": "exact" | "broader" | "related", "reason": "一句匹配程度表述" }
]
```

最多三条。挂靠成功后仍保留，方便用户改绑。

degree 与界面文案：exact = 精确对应；broader = 上级概念，偏泛；related = 相关但不同侧面。

只有 `degree === "exact"` 的首选才允许服务端在创建树时直接写入 global_node_id。否则 global_node_id 必须为 null。

### LocalNode

id, tree_id, parent_id（根为 null）, highlight_text（强制，根等于树的 anchor_highlight）, question_text（可空字符串）, title（6–12 字短标题）, answer_text, answer_original（「原文说的是」）, answer_extra（「补充解释」；若实现时拆不开，至少在 answer_text 里用两个小标题区分）, sources[]（{title, url}，不含历史问答）, created_at

根节点 parent_id 为 null，一棵树一个根。

### ExplorationRecord

不单独建表也可以。已挂靠的 LocalTree 本身就是记录。独立页按 `global_node_id = 该节点` 列 LocalTree，展示 article.title + 根 LocalNode.title + tree.created_at。

删除一棵树 = 删 LocalTree 及其全部 LocalNode。该全局节点若再无树，自然未点亮。

## 3. 接口（最低集）

认证：知乎 OAuth，session cookie 或 bearer。以下均需登录。

`GET /me`

`POST /articles/resolve` body: { zhihu_id, url, title, tags, lead } → 若已有该用户对该 zhihu_id 的 Article 则返回，否则判定学科、创建、返回。判定只在创建时发生。

`PATCH /articles/:id` body: { discipline_id } 用户点改学科标签。改学科后，该文已有局部树的挂靠一律清空为待挂靠（避免挂在错误的树上）。演示不走这条，但要有。

`GET /articles/:id/trees` 该文该用户的所有局部树（含节点）。用于重返文章恢复锚点。

`POST /trees` body: { article_id, anchor_paragraph, anchor_highlight, question_text } → 创建树和根节点，触发根回答生成（同步或返回 job，黑客松可同步等）。服务端完成：生成回答、短标题、最多三候选、若首选 exact 则写入 global_node_id。

`POST /trees/:id/nodes` body: { parent_id, highlight_text, question_text } → 追问。服务端带上整棵树上下文生成。不重新挂靠，不点亮新全局节点。

`PATCH /trees/:id` body: { global_node_id } 用户从候选里选，或从全局树手选。若手选的节点尚不存在：先 `POST /disciplines/:id/nodes` 建个人补充节点，再绑。

`POST /disciplines/:id/nodes` body: { parent_id, title } 个人补充。is_personal=true。不要让模型自己调这个接口。

`DELETE /trees/:id` 删整棵树。独立页用。

`DELETE /nodes/:id` 删该节点及全部后代。蒙版拖拽删除用。若删的是根，等价删树。

`PATCH /nodes/:id` body: { title } 改短标题。

`GET /disciplines` 第一层清单。

`GET /disciplines/:id/tree` 第二层整棵骨架（不含正文）。独立页一次拉完。

`GET /nodes/:id` 详情：节点字段 + 熟练度 + 该节点下的 LocalTree 列表（文章标题、根短标题、时间、zhihu url）。

`PATCH /nodes/:id/proficiency` body: { value } 旁路。

`GET /trees/:id` 整棵树带全部节点，供跳回展开。

生成类接口耗时。黑客松可以请求内直接等模型；若超过 30s，再改成 job + 轮询。不要为此先上队列。

## 4. 生成回答的服务端约定

### 4.1 输入拼装

系统侧固定规则（节选，完整 prompt 放 server/prompts/）：

你在帮助用户读懂一篇知乎专栏。兴趣探索，不是上课。

回答约 200 字。少用专业术语。先写「原文说的是」，再写「补充解释」。

不要引用用户以前的问答作为来源。不要提「作为 AI」。

只解释当前高亮。不要给未高亮的部分开新课。

用户消息结构：

```
# 文章
标题、tag、正文

# 本棵探索树
按树形打印每条：短标题、高亮、用户问题、回答。当前节点标记为 CURRENT。

# 当前高亮
...

# 用户问题
（空则「请解释这处高亮」）
```

根节点额外附加：

```
# 用户背景摘要
（历史探索的短摘要，供理解用，禁止当作事实引用）

# 本学科树骨架
节点路径列表（title / aliases / definition），用于产出挂靠候选
```

非根节点不要附学科骨架，不要附历史摘要。

### 4.2 输出 JSON（模型必须吐结构化）

```
{
  "title": "6到12字",
  "original": "原文说的是……",
  "extra": "补充解释……",
  "sources": [{ "title": "", "url": "" }],
  "candidates": [ { "node_id": "", "degree": "exact|broader|related", "reason": "" } ]
}
```

candidates 仅根节点需要，最多 3 条，按匹配度高到低。非根必须是空数组。node_id 必须来自输入骨架，禁止编造。

无合适节点时 candidates 为空。前端收到空数组且是根节点：打开全局树让用户自己加，不要弹「建议新增××」。

### 4.3 搜索

默认允许。由模型或服务端工具调用决定。来源写入 sources。官方文档、教材、原始资料优先。不要把本产品的历史问答 url 写进去。

### 4.4 短标题

即使模型没给，服务端用高亮文本截到 12 字兜底。不要用用户原问题截断。

## 5. 插件

### 5.1 匹配

`https://zhuanlan.zhihu.com/p/*` 仅此。

### 5.2 注入时机

页面就绪后读标题、tag、首段，调 `POST /articles/resolve`。在顶栏附近放学科小标签。

同时 `GET /articles/:id/trees`，按 anchor_paragraph + anchor_highlight 在正文里文本匹配，包一层 mark。匹配失败就跳过该锚点，不要把整篇文章刷黄。匹配策略：精确子串；失败则按段落纯文本去空白再找。本版本不考虑文章被改。

### 5.3 选区开树

mouseup 后若选区在文章正文内且非空，在选区末尾附近浮一个小按钮。点击：取选区所在段落的文本作为 anchor_paragraph，选区文本作为 anchor_highlight，打开蒙版，调用 `POST /trees`。

### 5.4 蒙版与布局

树容器 `position: fixed; top: 0; right: 0; height: 100vh;` 默认宽度约 360px。节点开始分叉、需要更宽时，增大宽度，并把文章容器 `margin-right` 设成同样的值，把知乎正文挤向左。知乎右侧栏（相关推荐）优先隐藏或挤出视口。

不要用 iframe 包知乎页。就地改 DOM。

底部删除栏平时隐藏。任一节点 `pointerdown` 超过约 400ms 进入拖拽，删除栏升起。拖入后 pointerup 调 `DELETE /nodes/:id`。不弹确认。

### 5.5 高亮追问

在已展开的回答文本上允许选区。选区非空才显示「追问」按钮或允许 Enter。调用 `POST /trees/:id/nodes`，parent_id 为当前回答所属节点。

箭头：从高亮 range 的包围盒连到子回答。用 SVG overlay，窗口 resize 和滚动时重算。滚动原文时，若高亮在原文里，箭头起点跟着走；回答内高亮则相对蒙版。

### 5.6 单击双击

click：选中并展开该问答。dblclick：toggle 子树展开。不要用 300ms 延迟模拟双击。

### 5.7 从独立页跳回

独立页打开 `https://zhuanlan.zhihu.com/p/{zhihu_id}?explore_tree={tree_id}`。内容脚本读 query，拉 `GET /trees/:id`，打开蒙版并展开。然后尽量 `history.replaceState` 去掉 query，避免刷新重复打开。

### 5.8 入口按钮

固定在蒙版或文章侧，打开独立页 `{APP_ORIGIN}/d/{discipline_id}`，可附 `node` query 以便独立页直接选中。

## 6. 独立页

路由建议：

`/login` OAuth 入口

`/d/:disciplineId` 某学科全局树

`/d/:disciplineId/n/:nodeId` 同上但右侧打开该节点详情

画布：根在左。非叶全部展开。叶默认不作为独立列，计数画在父节点上。单击父节点在其右侧原位插入一列叶子列表，已点亮淡黄。再单击移除该列。多组可同时开。

点任意节点（含展开后的叶子）：右侧详情。详情里的记录点击：`window.location` 到知乎 url + `explore_tree`。

点亮色、金 tag、n/N 的计算在前端用整棵树 + 该用户已挂靠的 global_node_id 集合做。后端 `GET /disciplines/:id/tree` 应同时返回 `lit_node_ids[]` 和每个 lit 节点的 record_count，避免独立页再扫全部树。

## 7. 学科树 JSON 格式（第二层 skill）

文件放 `disciplines/{slug}.json`。slug：`agent-app-dev`、`cognitive-psychology`、`distributed-systems`。

```
{
  "major": "人工智能",
  "name": "Agent 应用开发",
  "slug": "agent-app-dev",
  "origin": "preset",
  "nodes": [
    {
      "id": "stable-slug-or-uuid",
      "parent_id": null,
      "title": "Agent 应用开发",
      "aliases": [],
      "definition": "一句定义",
      "sort_order": 0
    }
  ]
}
```

id 必须稳定，生成骨架时就定下来，后面挂靠用这个 id。不要每次导入都换 uuid，否则已有 LocalTree 会断。

第一层 skill 可以是 `disciplines/index.json`：

```
[
  { "major": "人工智能", "name": "Agent 应用开发", "slug": "agent-app-dev" },
  { "major": "心理学", "name": "认知心理学", "slug": "cognitive-psychology" },
  { "major": "计算机系统", "name": "分布式系统", "slug": "distributed-systems" }
]
```

判定学科时只把 index 和文章标题、tag、首段给模型，输出一个 slug。不要把三棵整树都塞进判定上下文。

### 生成骨架的 prompt（开发时用来产出三份 JSON，人工再改）

你在为「知乎兴趣探索」预备一棵全局知识树。学科是：{name}。粒度是具体学科，不是大类。

要求：

树是权威目录结构，不是文章摘要。Agent 应用开发参考官方文档与公认课程大纲；认知心理学、分布式系统参考大学课程 / 经典教材目录。

每节点：title、aliases（常见别名与缩写）、definition 一句、parent。

深度大约 4～6 层。非叶节点是可展开的范畴，叶节点是可被一篇具体段落挂靠的概念。挂靠会大量发生在深的、具体的层，所以叶子必须具体，不要停在「记忆」「网络」这种大词。

不要写长正文。不要写例子。不要为了全而造假节点。

输出符合上面的 JSON。id 用英文 kebab-case 稳定 slug，在整棵树内唯一。

生成后必须人工看一遍：有没有大类混进来、有没有该在叶子的概念停在了太浅的层、Agent 应用开发那棵有没有把「人工智能概论」整棵塞进来（不应该）。

## 8. 点亮计算

```
lit(node) = exists LocalTree where global_node_id = node.id and user = me

gold(node) = lit(node) && every child c of node: lit(c)
             若 node 是叶子（无 child）：gold(node) = lit(node)

parent badge = count lit among (node 的全部后代 ∪ 可选是否含自身，产品要的是子树里被点亮的概念数)
建议：n = 子树内 lit 的节点数（含自身若 lit），N = 子树节点总数（含自身）
显示在非叶节点上，叶子收起时靠它看全貌。
```

金 tag 只是小标记，不要用它替代淡黄底。叶子点亮时：淡黄底 + 因为无子，同时带金 tag。若视觉太吵，金 tag 在叶子上仍要有，这是已定规则。

## 9. 权限与安全

模型密钥只在服务端。

OAuth token 只在服务端。插件拿自己的 session。

不要用非官方 zhihu-oauth 逆向库。

内容脚本不要 `innerHTML` 塞模型输出。回答按文本渲染，来源链接白名单 http/https。

删除接口必须校验 tree.user_id。

## 10. 建议实现顺序（下一会话按这个做）

1. 三棵学科树 JSON 生成并人工过一遍，导入后端。
2. 后端：User + OAuth 最小登录（黑客松若 OAuth 申请不下来，可先用开发用的固定测试用户，但代码路径按 OAuth 写）。
3. Article resolve + 学科判定。
4. LocalTree / LocalNode CRUD，先不接模型，用假回答打通。
5. 插件：选区、蒙版、右侧树、挤压布局、强制高亮追问、箭头、删除栏。
6. 接模型生成（200 字、短标题、候选挂靠、来源折叠）。
7. 独立页横向树、n/N、叶子原位展开、详情、跳回。
8. 点亮色、金 tag、重返文章锚点恢复。
9. 按设计文档第 14 节走一遍演示主线，断在哪修哪。

不要从独立页或视觉系统开始。没有蒙版里的树，独立页没有东西可回看。

## 11. 给下一会话的硬约束

不要新增产品规则。若实现时发现设计文档某条做不到，在文档里加「实现偏差」一节说明，不要悄悄改产品。

不要给回答加「相关概念」推荐、不要自动点亮高亮里提到的其他节点。

不要做联网开关 UI。

不要在回答底部列出历史探索。

学科判定失败时（模型没吐出三棵里的 slug）：仍创建 Article，discipline_id 先空，界面提示用户点选三棵之一。这是实现兜底，不是产品上的「跨学科」。不要为此去匹配大类。
